# 0049. Wake feedback: earcon, "didn't catch that" cue, tray, latency line, debug aid

- Status: Accepted
- Date: 2026-11-28
- Amends: 0041

## Context
The owner found Footman unresponsive: the wake word and command had to be said several times before anything was heard or seen. The journal showed three things.

- Nothing told the user the wake word had been heard. `core.Config.Earcon` existed, but the daemon never set it, so the first sound was the spoken reply 5 to 25 s later (or the acknowledgement clip, about a second after the end of speech).
- About 18% of the spotter's wakes were dropped by the second stage (ADR-0041), silently, so a real wake that the speech-to-text check did not confirm looked the same as a wake the spotter never heard. The text is deliberately not logged, so the cause (what the engine heard) was invisible.
- The `turn N: ... ok` line is logged after playback ends, so time-to-first-audio was unknown.

## Decision
- **Wake earcon.** When the spotter fires (and a dictation session is not running), the daemon plays a built-in earcon: two soft rising sine notes (880 and 1318.5 Hz, 150 ms in all, peak 0.12, about -18 dBFS, 10 ms raised-cosine fades), generated in Go (`audio.WakeEarcon`, 24 kHz mono) so there is no sound file and no licence. It starts in the background the moment the wake is reported, before the second stage. The same clip is the cue when a follow-up window opens (ADR-0047), which `Config.Earcon` always was for. Quiet mode silences it. `speech.wake.earcon` (default true, voice-settable, applied live) switches it off.
- **Echo and the microphone.** The microphone stays open while the earcon plays. It is short and soft, so it cannot start a turn on its own (a segment must leave `MinCommand`, 250 ms, after the wake word; the earcon is 150 ms) and a speaker that leaks it into the microphone only adds a faint blip to the start of the command audio, which speech-to-text ignores and the second stage reads past. The follow-up fence is unchanged: the follow-up cue is still played to its end before the fence is measured (ADR-0047), and the wake earcon is not a follow-up window, so no fence applies.
- **"Didn't catch that" cue.** When the second stage rejects a wake because speech was heard that did not start with a wake word (`no_wake_word`), a softer, lower, falling two-note cue (392 and 294 Hz, 150 ms, peak 0.07; `audio.MissCue`) plays, so the user knows to say it again. It is not played for `no_speech`: an empty transcript is almost always a false wake of the spotter in background noise, and answering those would add a cue to every noise-triggered earcon. It is silenced by quiet mode and by `speech.wake.earcon` false.
- **Tray.** From the wake word until the command is claimed (or the wake window expires) the microphone status is `Recording` (published on `pipeline.mic`, and passed to the tray), then it goes back to `WakeListening`. A false wake flickers the status for a moment, which is accurate: the microphone is capturing speech for a possible command.
- **Latency line.** Each spoken command turn publishes `pipeline.timing` (`core.TurnTiming`) and the journal logs one line, never text: `turn 4: timing (ms): wake->speech end 2310, transcribe 201, ack 410, first token 1450, first audio 3120; wake->first audio 5430`. `wake->speech end` is the wake word being heard to the VAD handing over the utterance (it includes the VAD's `min_silence`). `ack`, `first token` and `first audio` are counted from the end of speech: the first sample of the acknowledgement clip, the first text from the AI, and the first sample of the spoken reply. `wake->first audio` is the sum of the first and last. Steps that did not happen (a fast-path command has no token; a reply that is only shown has no audio) are left out; typed text has no end of speech and logs no line. It is published for command turns only.
- **Debug aid.** `speech.wake.debug` (default false, applied live, not voice-settable) adds what the engine heard to the rejection line, quoted and cut to 60 characters: `turn 7: wake word not confirmed by speech-to-text (no_wake_word; 0.8 s checked in 201 ms), dropped; heard "all fred open the door"`. This breaks ADR-0041's rule that the text of a rejected wake is never logged, which is why it is opt-in: with it on, speech picked up near a wake word (possibly a conversation in the room) is written to the journal. The text is on the bus event only when it is on, and the local API never sends it. Turn it off after tuning.
- **Looser second-stage match.** `Router.MatchWake` accepts a greeting before the name ("Hey Alfred", "Hello Klaus": `hey`, `hi`, `hello`, `yo` join the fillers, still at most two), and a name of six or more letters also matches a word with the same first three letters within two edits ("Alfie" for "Alfred"). The spotter must have fired first, so the second stage only has to tell the wake word from other speech; both changes keep "the Alfred Hitchcock film", "Alpha" and "Ashley" rejected. "Al Fred", "Alfredo", "Claus", "Klaus," and "Close" (same consonants as "Klaus") and "Ash ford" were already accepted and now have tests.

## Consequences
- The user hears a blip within the player's start-up time (25 to 35 ms, ADR-0026) of the spotter firing, instead of nothing for seconds. Every spotter hit plays it, including the 1 to 2 false wakes an hour at boost 3 (ADR-0041); `speech.wake.earcon` false turns that off.
- The miss cue arrives after the VAD's `min_silence` plus one transcription (about 0.7 s after the end of speech), so "wake word not confirmed" is now audible.
- `speech.wake.debug` output tells whether the 18% of dropped wakes are spelling the match can learn (add the spelling) or words the engine really did not hear (a spotter or microphone problem). Loosening further should wait for that evidence.
- Not done: wakes that the spotter misses entirely still leave no trace. Seeing them needs the spotter's near-misses or an always-on transcript, both of which break the privacy rule for good; this is left to the owner.
